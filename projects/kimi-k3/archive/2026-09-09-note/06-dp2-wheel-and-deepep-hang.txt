### 10.6 改的原因 + 方案（2026-09-03）：auto→normal 的取舍与长期目标
**改的原因**：混部配方是 `dp2pp4tp16`——4 机、PP4、每机 TP16、DeepEP、还要 decode 开图。EP 组 = TP = 一台机器上的 16 张卡。`--deepep-mode auto` 时 decode 走 low-latency：布局是固定长度（才能进图），但 NPU 实现里**同机仍走 RDMA（`num_rdma_bytes`），HCCS 捷径没接上**。同机 16 卡 all-to-all 走网卡 QP，通道会脏 → 请求卡死 → ~十来分钟进程退出。这不是 tokenizer，也不是 `--cuda-graph-bs` 没写上。

| 已经验过的 | 结果 |
|---|---|
| auto + 图 | 能 capture，推理卡死（有时第一发，有时第 2 发） |
| normal + DeepEP | 第 1、第 2 发 grab_logprob 都过，内容和 8-30 终验一致 |
| normal 下的图 | moe_hook 强制关掉：normal 是变长 layout，不能 capture |
| normal 同机 | 走 HCCS（`intranode_dispatch`）所以稳；图没了是布局变长，**不是 PP 和 DeepEP 互斥** |

补充：关 DeepEP 图大概能开，但会退回 TP-MoE + allreduce、decode 慢一截，且与 §9「DeepEP + DP attn + shared expert 切分」绑在一起、精度不保险（社区关 DeepEP 那次是乱码，配方还不一样）。

**现在能服务（已采用）**：保持 `--moe-a2a-backend deepep --deepep-mode normal`，接受没图。

**目标（DeepEP + PP + 图，decode 还不按 capacity pad）**：修 sgl-kernel-npu 里 default LL——`low_latency_dispatch` / `combine` 对**同机 rank 走 HCCS（`num_nvl_bytes` / `intranode_*`）**，跨机仍 RDMA；sglang 继续 auto，hook 不再关图。
- 不是 `DEEP_USE_MODE=alltoall`（HCCL + 每步 pad），也不是关 DeepEP；alltoall 最多当对照。

**10.6 静态核查结论（2026-09-03）** —— 修正原方案里两处与实现不符的判断：
1. `comm_alg = "hierarchy"` **根本不存在**，且不在要改的层。low-latency 的 tiling 校验（`moe_distribute_dispatch_v2_tiling.cpp` 的 `CheckAndSetSpecialExpertInfo`）只认 `fullmesh_v1/v2/ccu`，kernel 端（`moe_low_latency_dispatch_v2.cpp`）也没有 hierarchy 模板——直接传会挂 `commAlg is invalid`。
2. RDMA/HCCS 差异既不在 `comm_alg` 也不在 MCC 算法串：normal 与 low-latency 用**同一串** `AlltoAll=level0:fullmesh;level1:pairwise`，kernel 里 peer 寻址都是同一个 `GetBaseWindAddrByRankId`（self→`localWindowsIn`，peer→`remoteRes[].windowsIn`）。

**根因**：EP 组=同机 16 卡，但 low-latency 走的 `aclnnMoeLowLatencyDispatchV2` / `CombineV2` 这个算子**没有 intra-node 数据面**；normal 走 `aclnnCamMoeDispatchNormal`+`CombineNormal` 时 `intranode_dispatch` 自带 HCCS 数据面 → 所以 normal 稳、LL 走 RDMA。A3 buffer 的拓扑探测本身是对的（`num_nvl_ranks=num_ranks`、`num_rdma_ranks=1`）。

**真正要改的点**：让 `MoeLowLatencyDispatchV2/CombineV2`（A3/`__DAV_C310__`）具备 intra-node HCCS 数据面——把 `cam_moe_dispatch_normal.h` 里 `intranode` 窗口寻址逻辑（`localWindowsIn`/`remoteRes`）落到 low-latency v2 的 kernel/tiling（`moe_low_latency_dispatch_v2.cpp`、`moe_distribute_combine_v2_*`），跨机仍走 RDMA。kernel 级改动，需 A3 硬件验证。

**已落地（诊断，可逆，`DEEPEP_LL_DEBUG` 门控）**：`deep_ep.cpp` 的 `low_latency_dispatch`/`combine` 各加一段 stderr 打印（soc / ranks / rdma_ranks / nvl_ranks / comm_alg / ep 组名）。下次 `auto+图` 复现设 `DEEPEP_LL_DEBUG=1` 确认 LL 实际走的层与参数，再对症改 v2 kernel 的窗口/数据面。
