## 5. K3 KDA forward_decode IndexPutImpl dtype 错误 (踩坑)

**症状** ([personal/sglang/.../ascend_kda_backend.py:152-163](file:///home/<USER>/personal/sglang/python/sglang/srt/hardware_backend/npu/attention/ascend_kda_backend.py#L152-L163))：
```
File "sgl_kernel_npu/mamba/causal_conv1d.py", line 1371
    out, conv_state[conv_state_indices] = torch_causal_conv1d_update_npu(...)
RuntimeError: _index_put_impl_ ... aclnnIndexPutImpl failed, error 161002
AclNN_Parameter_Error(EZ1001): Tensor selfRef expected DT_FLOAT but found DT_BFLOAT16
```

**根因**：
- K3 mamba cache 的 `conv` 默认 dtype = bf16 ([inkling.py:412](file:///home/<USER>/personal/sglang/python/sglang/srt/configs/inkling.py#L412))
- `sgl_kernel_npu` 的 `causal_conv1d_update_npu` 内部用 fp32 算，in-place `index_put` 写回时目标 dtype 是 bf16 → NPU 拒
- 和 PP 无关：baseline (pp=1) 不炸是因为它**默认 dspark on**，main generation 走 `_forward_target_verify` ([L374](file:///home/<USER>/personal/sglang/python/sglang/srt/hardware_backend/npu/attention/ascend_kda_backend.py#L374))，**绕开** `forward_decode` 里的 `causal_conv1d_update_npu`
- newbase (pp=4) 关 dspark → 走 `forward_decode` → 撞 dtype bug

**临时 workaround**（不推荐长期，仅临时跑通）：
```python
# 在 ascend_kda_backend.py forward_decode 调 kernel 前 cast 一次，持久化到 cache
if conv_states.dtype != torch.float32:
    conv_states = conv_states.float()
    layer_cache.conv[0] = conv_states
```

**治本方向**（3 选 1）：
1. 改 `sgl_kernel_npu` 的 `causal_conv1d_update_npu` 接受 bf16 conv_state（内部 cast）
2. 改 [inkling.py:412](file:///home/<USER>/personal/sglang/python/sglang/srt/configs/inkling.py#L412) 让 K3 mamba cache 默认 fp32（HBM 翻倍）
3. **本次采用：newbase 改成 dspark on**（绕开 forward_decode 路径）— 这是为什么 newbase 现在 dspark 注释被打开

**为什么 mixed.sh 之前禁 dspark**（"DSPARK conflicts with PP"）：Dspark verify 路径用 `forward_verify`/`_forward_target_verify`，跟 PP=4 通信组的兼容没在 mixed 那轮验证过；本轮 newbase 是第一次真把 dspark 配 PP 起来。
